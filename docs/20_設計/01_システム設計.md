## 1. 設計方針

| # | 原則 | 理由 |
|:-:|---|---|
| 1 | **3層を疎結合にする**（知覚／計画／制御） | 上位層が未完成でも下位層だけで動画が撮れる＝段階的縮退（方針 §4）を成立させる |
| 2 | **層の境界はデータ構造で定義する** | 差し替えだけでアブレーション（AIあり/なし）が実施できる |
| 3 | **設定値をコードに埋めない** | 再現性のため。実験ごとに設定を残す |
| 4 | **既定値を実験で書き換えない** | 過去に「A/Bで勝った値を既定へ書き込み、以後の全実験の基準が変わった」失敗がある |
| 5 | **すべての動作に上限を持たせる** | 無限待ちを作らない。失敗は失敗として記録する |

## 3. 各層の責務とインタフェース

### 3.1 計画層（Planner） — **L2 / L3 とも実装済み**

| 項目 | 内容 |
|---|---|
| 責務 | 日本語の指示を、実行可能な手順に分解する |
| 入力 | 指示文（例:「飲み物を左の箱へ、食べ物を右の箱へ」） |
| 出力 | `list[Step]`。`Step(target="Milk", destination="左の箱")` |
| **L2（rule）** | カテゴリ辞書による文字列一致。`src/envs/pickplace.py` の `CATEGORY_RULES` |
| **L3（llm）** | **`Qwen/Qwen2.5-1.5B-Instruct`**（3.1GB、推論のみ）。`src/planning/llm_planner.py` |
| 出力形式 | **JSON に強制**。パース不能なら最大2回作り直し、それでも駄目なら**手順を出さない** |
| 落とすもの | シーンに無い物体・未定義の配置先は**理由を付けて落とす**（黙って別の物へ置き換えない） |
| 失敗時 | 手順が1つも生成されなければ **F-1** として記録 |

> **L2 と L3 は戻り値の型が同じ**なので、差し替えるだけで条件 C3 対 C4 の比較になる。

#### few-shot の例は**2要素**にする（実測で決めた。DEC-22）

| 例の要素数 | 1.5B の「期待どおりの手順」 | 3B |
|:-:|:-:|:-:|
| 1要素 | 0/10 | 0/10 |
| **2要素** | **10/10** | 0/10 |

モデルは**例の長さを真似てしまう**。1要素の例を見せると、1〜2要素しか出さなくなる。
**大きいモデルが良いとは限らなかった**（3B は 1.5B に負けた）。

#### 実行順の正規化（DEC-23）

計画層の出力は、実行前に **`normalize_plan_order()`** で基準順（Milk → Can → Bread）へ並べ替える。

| 実行順 | 手順成功 |
|---|:-:|
| **順A Milk→Can→Bread（基準）** | **41/60** |
| 順B Can→Milk→Bread | 29/60 |
| 順C Bread→Milk→Can | 34/60 |

**順番だけで 12手順動く**（真値をAIへ置換したコスト 4手順の**3倍**）。
順番は指示の意味に含まれないので、正規化しても「言語を理解した」という主張は損なわれない。
**なぜ順Aが良いかの機構は未解明**（S-11）。経験的に選んでいる。

### 3.2 知覚層（Perception） — **実装済み** `src/perception/owlvit_detector.py`

| 項目 | 内容 |
|---|---|
| 責務 | 画像から、指定された語に対応する物体の位置を返す |
| 入力 | RGB画像（512×512）、深度画像、探す語 |
| 出力 | `{label, score, bbox, pixel, position_3d, source, identified_correctly}` |
| **モデル** | **`google/owlv2-base-patch16-ensemble`**（622MB、推論のみ） |
| **画角** | **卓上を切り出す**（比率 0.02, 0.25, 0.56, 0.72） |
| **問い合わせ語** | **各物体2語・計8語**（例: Milk は `a carton of milk` / `a milk box`。**意味語のみ**。正は `TEXT_QUERIES`） |
| 実装（L1縮退 / 条件 C0） | シミュレータの真値を返す（`source="ground_truth"`） |
| 検証 | **T-1〜T-3 は3つとも合格**（画像も語も実際に使われている） |

> **`source` フィールドを必ず持たせる**（`"model"` / `"ground_truth"`）。
> どの条件で取った結果かがログだけで判別でき、アブレーションの取り違えを防ぐ。

#### 2D → 3D の変換（実測で決めた。DEC-16）

**深度画像を読むと系統的にずれる。** 得られるのは物体の**手前の面**の座標であり、中心ではない。

∴ **同定ができていれば物体の高さは既知**なので、
検出枠の中心を通る視線と、**その物体の中心高さの水平面**との交点を使う。

| 位置の求め方 | 手順成功 | 同定精度 |
|---|:-:|:-:|
| 深度画像を読む | 15/60 | 53/60 |
| **視線と平面の交点** | **40/60** | 53/60 |

**同定精度が両条件で同一**なので、差は位置の求め方だけで説明できる。
使う高さは**物体のカタログ値（形状）**であり、その場の真値位置ではない。

#### 把持姿勢の向きをAIから求める（実測で決めた。DEC-19）

検出枠の中で深度を使って物体と机を切り分け、**上面付近の点だけ**の最小外接矩形の傾きを使う。

| 点の選び方 | 誤差中央値 | 15度以内 | 判定 |
|---|:-:|:-:|---|
| 机より上の点すべて（`minrect`） | 25.3度 | 22.9% | **ランダム以下。使わない** |
| **上面付近の点だけ（`top_face`）** | **1.8度** | **71.4%** | **採用** |
| ランダム（基準線） | 23.2度 | 32.2% | — |

**なぜ側面を除くのか**: 見えているのはカメラ側の面だけなので、点群は物体の輪郭ではなく
**視線方向に引き伸ばされた殻**になる。その最小外接矩形は**カメラの向き**を反映してしまう。
上面の輪郭はほぼ物体の footprint そのものなので、向きが素直に出る。

**推定できないときは `None` を返す**（推定したふりをしない）。味方は固定向きへ退く。

#### 制約

| 制約 | 内容 |
|---|---|
| 向き推定 | **上面が見えていることが前提**。見えない配置での振る舞いは**未確認** |
| Cereal | 5回中2回未検出（F-3。未決 S-08） |
| 入力の精細さ | 実写で学習されたモデルなので、**描画が粗いと性能が落ちる** |

### 3.3 制御層（Controller） — **実装済み** `src/control/primitives.py`

| 項目 | 内容 |
|---|---|
| 責務 | 目標位置に対して、掴む・運ぶ・置く を実行する |
| 入力 | 目標位置（3D）、**物体の向き（ヨー角）** |
| 出力 | robosuite への行動ベクトル（action_dim=7、実測） |
| 実装 | 動作プリミティブ `move_to` / `pick` / `place` / `hold`。位置は比例制御、姿勢は z 軸まわりのヨー角を物体に合わせる |
| 終了判定 | 各プリミティブに**ステップ上限**と**詰まり検知**を持たせる |

#### 把持姿勢の向き合わせ（実測で効果を確認済み。DEC-14）

平行2指グリッパは向きが合っていないと物体の**対角線**を掴むことになり、実測で物体を倒した。
グリッパは 90 度回しても同じ掴み方になるため、**角度誤差を ±45度に畳んでから**制御する。

| 条件 | 手順成功率 |
|---|---|
| 向き合わせなし | 2/12 |
| **向き合わせあり** | **9/15** |

#### 物体ごとの把持点補正（実測で決めた値。DEC-09）

| 物体 | z 補正 [m] | 単体試行の持ち上げ成功率 |
|---|:-:|:-:|
| Milk | +0.02 | 4/5 |
| Bread | -0.01 | 4/5 |
| Can | 0.00 | 5/5 |
| Cereal | — | 2/5（**対象外**） |

根拠: [experiments/exp001_grasp_sweep](../../experiments/exp001_grasp_sweep/README.md)（80試行）

#### 手を離す高さ

高い位置から放すと落下の衝撃で物体が倒れ、箱の外へ出る（実測で F-7 の原因）。
∴ 解放位置を **箱の底 + 物体の半高 + 把持点補正 + 1cm** で計算する。
同じ箱に複数入れるときは置き場所をずらす（重ねると崩れて箱の外へ出る）。

### 3.4 記録層（Recorder） — **実装済み** `src/recording.py`

| 項目 | 内容 |
|---|---|
| 責務 | フレーム・実行ログ・指標を残す |
| 出力 | `outputs/<run_id>/video.mp4`, `events.jsonl`, `summary.json`, `config.json` |
| 実装 | `MUJOCO_GL=egl` でオフスクリーン描画 → **ffmpeg に生フレームを流して H.264（CRF 23）** |
| 予備経路 | ffmpeg が使えないときは OpenCV(mp4v) |
| **重ね表示** | 指示の進行（`step N/M`）と**知覚AIの検出枚**を描く。音声無しでも分かるように |
| 注意 | **`run_id` は日時＋タグ**。同じフォルダに上書きしない |
| 画像の向き | **robosuite のカメラ画像は上下が反転している**。記録時に戻す |
| **重ね表示の制約** | **cv2 は日本語を描けない**。画面上は英数字に限り、日本語は編集で足す |

> **H.264 にした理由（DEC-13）**: 同じ内容・同じ長さの動画が
> **OpenCV(mp4v) で 8.1MB → H.264 で 1.7MB**（実測）。容量制約 R-07 に大きな余裕が生まれる。

## 4. データ構造（層の契約）

```python
# 知覚層の出力（src/pipeline.py: locate）
{
    "label": str,                    # 検出した物体の語
    "score": float,                  # 確信度 0-1
    "position_3d": np.ndarray,       # ワールド座標 (x, y, z)
    "yaw": float,                    # z軸まわりの向き [rad]。把持姿勢に使う
    "source": str,                   # "model" | "ground_truth" ← 条件の取り違え防止
    "identified_correctly": bool|None,  # 同定の正誤（真値条件では None）
}

@dataclass
class Step:          # 計画層の出力1件
    target: str      # 対象物体の語
    destination: str # 配置先（"左の箱" | "右の箱"）

# 手順の結果（events.jsonl の1行）
{
    "target": str, "destination": str,
    "success": bool,
    "failure_mode": str | None,   # F-1〜F-9。定義は 02_評価設計.md
    "elapsed_sec": float,
    "lift_height_m": float,       # 持ち上げ**直後**に測る（配置後だと意味が変わる）
    "source": str, "identified_correctly": bool | None,
}
```

## 8. 実装上の注意点（実測で踏んだ罠）

| # | 現象 | 対処 |
|:-:|---|---|
| 1 | robosuite のカメラ画像は**上下が反転**している | 記録層・知覚層で `np.flipud` してから使う |
| 2 | インタプリタ終了時に `EGLError` が出る | **無害**（描画コンテキストの解放順序）。失敗と誤読しない |
| 3 | 持ち上げ量を**配置後に測ると意味が変わる** | 把持判定は**持ち上げ直後**の値を使う（実際に誤判定を出した） |
| 4 | 単体試行での成功率が連続タスクで再現しない | **通しで測る**。部品単体の数値を全体に外挿しない |
| 5 | 成否の基準に**推定位置を使うと誤差が成否に混ざる** | 持ち上げ量の基準は**常に真値の初期位置** |
| 6 | transformers 5.x で `post_process_object_detection` が改名 | `post_process_grounded_object_detection` を使う |
