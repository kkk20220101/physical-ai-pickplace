# コードと文書の横断レビュー結果（N系・2026-09-29）

**位置づけ**: **要件と実装の一致／再現性／依存関係の正**。
**目的**: これまでの検査は「提出物が壊れていないか」に寄っていた。
今回は**要件・設計・コード・文書を突き合わせ、言っていることと実物がずれていないか**を見た。

**結論**:
- **5件の不一致が出た。** うち **1件は実行時に例外で落ちる実害**（GPU の無い機械）。
- **1件は「文書が用意すると書いた実物が無い」**（`requirements.txt`）。
- 残り3件は**状態表記・数値の陳腐化**。
- **全件修正し、フルチェーンで回帰が無いことを確認した。**

### 1-1. なぜ #1 が最も重いか

提出物は**採点者が動かす可能性がある**（要項 §6.2 でコード公開が評価対象）。
**こちらは GPU のある機械しか持っていないので、この欠陥は手元では 100% 露見しない**
——リスク R-33（「手元では必ず成功する」型）の4件目である。

## 2. 意思決定

| ID | 決めたこと | 理由 |
|---|---|---|
| **DEC-52** | **推論デバイスは `src/device.py` が実行時に判定する**（`cuda` が使えれば `cuda`、無ければ `cpu`） | 採点者の機械は選べない。**計測機では `cuda` に解決されるので数値は動かない** |
| **DEC-53** | **`requirements.txt` を置き、allow-list にも明示する** | 再現性は加点観点（技術力）。**allow-list はフォルダ粒度なので直下ファイルは書かないと出ない** |

**制約**: **C-36**（デバイスを固定しない）／**C-37**（`requirements.txt` を公開物に含める）。

### 3-1. 互換性

`requirements.txt` の `torch==2.7.1` は**版だけを固定し、CUDA/CPU の別は index-url に委ねる**。

取得元の指定方法をファイル冒頭に注記した。

## 5. 副産物 — 自分の文書が自分の規則を破っていた

`requirements.txt` を allow-list へ足した直後、公開検査が**新たに1件で止まった**。
止めたのは**前回作った `20260929_公開物の個人パス検査_結果.md` 自身**で、
**欠陥の事例として個人のホーム配下の絶対パスと他プロジェクト名をそのまま引用していた**。

> **欠陥を説明する文書が、同じ欠陥を再生産していた**（DEC-31 と同型）。
> **事例を書くときは中身を伏せ字にする**——`/home/<user>/...` へ置換して解消した。
> **ブロッキングにしていなければ、この文書はそのまま公開されていた。**
