## 1. PDF 変換経路の実測比較

### 1-1. この環境で使えるものを先に数えた

「どれが速いか」ではなく **「そもそも入っているか」** から確かめた。

| 候補 | 有無 |
|---|:-:|
| pandoc / XeLaTeX / LuaLaTeX | **無** |
| weasyprint / wkhtmltopdf | **無** |
| Chromium / Chrome（headless print） | **無** |
| playwright | **無** |
| **LibreOffice 24.2.7.2** | **有** |
| **PyMuPDF 1.28.2（Story + DocumentWriter）** | **有** |
| markdown 3.7 / Pillow / fontTools 4.63 | 有 |

∴ **比較できるのは2経路しかない。** 両方を同じ原稿で走らせて数字で決めた。

### 1-2. 実測（同一原稿・同一図6枚）

| 指標 | PyMuPDF Story | **LibreOffice** |
|---|---:|---:|
| ページ数 | 6 | 10 |
| **容量** | **50.2 MB** | **0.70 MB** |
| 容量（deflate 後） | 30.3 MB | — |
| 容量（font subset 試行後） | **27.6 MB**（※失敗） | — |
| 日本語の抽出 | 2,205字 | 2,267字 |
| 日本語スパンのフォント | NotoSansCJKjp | NotoSansCJKjp ほか |
| 図の埋め込み | 6/6 | 6/6 |
| 生成時間 | 1.1 秒 | 1.3 秒 |

**採用: LibreOffice（DEC-30）。容量が 97 分の 1 である。**

### 1-3. なぜ PyMuPDF が 50MB になったのか

**図ではなくフォントが原因だった。** 図の実体は 6枚で 388KB しかない
（PDF 内から取り出して確認: 58KB, 45KB …）。

膨らんでいたのは **埋め込まれた Noto Sans CJK JP（Regular と Bold で約 32MB）**。
`Document.subset_fonts()` で削ろうとしたが
**`MuPDF error: format error: Reserved charstring byte c=0x0` で失敗**し、27.6MB までしか落ちなかった。
LibreOffice は同じフォントを**部分集合化して埋め込む**ので 0.70MB で済む（**72分の1**）。

> **訂正（2026-09-29）**: 本表の LibreOffice 列は当初 0.52MB／2,196字／9〜11ページと
> 書いていたが、**その値と突き合わせられる一次情報が現存しない**
> （残っている実測は `experiments/exp007_pdf_route/out/result.json` ＝ 0.70MB・2,267字・10ページ）。
> 素性の分からない数値は使わない方針に従い、現存する実測へ置き換えた。**採否（LibreOffice 採用＝DEC-30）は不変**。

> **一般化**: **日本語 PDF の容量は図ではなくフォントで決まる。**
> CJK フォントは1書体 16MB 級なので、**部分集合化できない経路は最初から使えない。**

### 1-4. MuPDF は `.ttc` を CSS から読めない

`@font-face { src: url(/usr/…/NotoSansCJK-Regular.ttc) }` は
`format error: cannot locate font` で落ちた。この環境の日本語フォントは
**`.ttc`（コレクション）しか無い**ため、比較のために fontTools で
`.otf` を取り出す必要があった（`experiments/exp007_pdf_route/`）。
**採用しなかった経路の話なので、本番スクリプトにはこの処理を残していない。**

## 2. 実装

| ファイル | 役割 |
|---|---|
| `scripts/build_submission_package.py` | 原稿 → PDF → 規定ファイル名 → Zip |
| `scripts/check_submission.py` | Zip を検査（12項目のうち**機械で判定できるものだけ**） |
| `experiments/exp007_pdf_route/probe_pdf_routes.py` | 上の比較に使った実測スクリプト |

### 2-1. 社内向けメタ情報を落とす

原稿の先頭には `最終更新` `状態: PDF化とファイル名付与が未` が書いてある。
**そのまま出すと「作りかけです」と書いた資料を提出することになる。**
`strip_internal_front_matter()` が H1 直後から最初の `---` までを落とし、
提出用のタイトル（`指示文から物体を仕分けるロボット` / `Physical AI 最終課題 説明資料`）に差し替える。
**落とせたかどうかも機械で判定する**（本文冒頭に「最終更新」が無いこと）。

### 2-2. 図が紙面からはみ出ていた（検査を足して発見）

初版は **6枚すべてが右端で切れていた**。原因は
**LibreOffice の Writer/Web が CSS の `img{width}` も HTML の `width` 属性も無視し、
PNG 自身の寸法（px と DPI）で配置する**こと。

| 対策 | 結果 |
|---|---|
| CSS `img { width: 15cm }` | **効かない** |
| HTML `<img width="580">` | **効かない**（737pt のまま） |
| **変換前に PNG を 620px へ縮小（`stage_figures`）** | **収まった**（11ページ→9ページ） |

> **運用ルール**: **「埋め込まれている」と「紙面に収まっている」は別の検査である。**
> `verify_pdf()` は画像の配置矩形がページ矩形に収まっているかを見る。
> **枚数だけ数えていたので初版は素通りした。**

## 6. 公開前確認でつまずいた2点（どちらも検査器側の欠陥）

### 6-1. allow-list はフォルダ単位なので、中の生成物まで拾う

`experiments/` を許可しているため、**比較用に作った 50MB の PDF が公開対象に入った**
（公開対象が 70 → 92 ファイルに増えた）。

**修正**: **実際に公開されるのは git が追跡するものだけ**なので、
`check_publish_safety.py` が **`.gitignore` も通す**ようにした（DEC-32）。
`experiments/**/out/` と `*.otf` を `.gitignore` に追加した。

> **一般化**: **許可一覧（何を出すか）と除外一覧（何を出さないか）は両方要る。**
> 許可だけだと**フォルダの粒度でしか守れない**ため、その中の生成物が素通りする。

### 6-2. 検査結果そのものが検査に引っかかった

検査結果 JSON を `docs/30_評価/`（公開対象）へ書いていたため、
**JSON に書き出した「検出した禁止語」が、次の実行で禁止語として検出された。**

**修正**: 検査結果の既定の出力先を **`outputs/publish_safety.json`（公開対象外）** にし、
出力先ファイル自身を走査対象から外した（DEC-31）。

> **一般化**: **禁止語を探す道具の出力には、必ず禁止語が載る。**
> ∴ **その出力を公開領域に置いてはならない。**

### 6-3. 修正後の結果

|---|---|
| 公開対象ファイル数 | **70**（`.gitignore` で除外 24） |
| 禁止語の検出 | **0 ファイル** |
| 大きいファイル（>20MB） | 0 |
| 禁止拡張子 | 0 |
| **判定** | **公開可** |
