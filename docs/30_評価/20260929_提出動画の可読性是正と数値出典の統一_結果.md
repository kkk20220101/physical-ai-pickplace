# 提出物の可読性是正と「数値の出典」の統一（2026-09-29）

**位置づけ**: **提出物のサイズ・動画の内容・PDF の体裁に関する数値の正**（20260928 の各文書の該当値を置き換える）。
**きっかけ**: **人の目視のために動画を初めて実際に見たところ、3つの欠陥が同時に見つかった。**
機械チェックは**全項目 OK のまま**だった。
**同日の2巡目で PDF を初めて見たところ、また3件出た**（§7）。

**結論**:
- **「機械チェックが通っている」と「提出物として成立している」は別である。** 計6件とも機械は無言だった。
- **最も重かったのは容量でも滞みでもなく、提出物が自分自身と違う主張をしていたこと**（動画: `10/15` 対 `41/60`／PDF: 「7条件」対 4行）。
- 再発を止める仕掛けを**すべて機械側に入れた**（警告の失敗扱い・出典の一本化・単位の統一・**数値台帳**・**罫線の数え上げ**）。

## 1. 調査結果 — 目視で見つかった3つの欠陥

| # | 欠陥 | 機械の反応 | 重さ |
|:-:|---|---|---|
| **1** | **まとめスライドが `10/15`・`12/15` と表示していた**。直前のグラフは `41/60`・`53/60` | **無言**（OK） | **最重**。同じ動画の中で主張が食い違う |
| **2** | **アブレーション図の説明文が丸ごと消えていた** | **無言**（終了コード 0） | 中。説明が1行欠落 |
| **3** | 焼き込み文字が拡大でにじむ／背景に溶ける | **無言** | 中。読めない |
| **4** | 同じファイルが `2.90MB` とも `2.99MB` とも報告されていた | **無言** | 小だが文書が割れる |

### 1-1. 欠陥1 — 数値の出典が2つあった

動画のまとめは**素材 run の `summary.json`** を読んでいた。
だが素材 run は**見せるための5エピソード（15手順）**であり、
グラフが使う**アブレーションは20エピソード（60手順）**である。

| 表示箇所 | 読んでいた出典 | 表示していた値 |
|---|---|---|
| グラフ（fig3） | `experiments/exp003_ablation/result.json` | **41/60・53/60** |
| まとめスライド | 素材 run の `summary.json` | **10/15・12/15** |

**10/15 = 40/60 であって 41/60 ではない。** 丸め誤差でも表記ゆれでもなく**別の実験の数字**だった。

> **一般化**: **同じ量を2か所から読んだら、いつか必ず食い違う。**
> **図に数値を手打ちしない（DEC-28）だけでは足りない**——
> **「手打ちしない」と「同じ出典から読む」は別の規律**である。

### 1-2. 欠陥2 — `%` が drawtext を黙って壊す

**実測**（`ffmpeg` 7.x・同一コマンドで文字だけ変えた）:

| text | stderr | 終了コード | 生成物 |
|---|---|:-:|---|
| `上限の91%` | `Stray % near ''` | **0** | **880 B（真っ白＝文字なし）** |
| `上限の91\\%` | なし | 0 | 4,988 B（文字あり） |
| `上限の91％`（全角） | なし | 0 | 4,990 B（文字あり） |

**`%` は drawtext の展開記号**であり、逃がさないと**その drawtext が丸ごと捨てられる。**
しかも **`ffmpeg` は終了コード 0 を返す**ので、戻り値だけを見ている呼び出し側は成功と判断する。

> **∴ 「異常終了しなかった」は「やりたいことができた」を意味しない。**

### 1-3. 欠陥4 — `MB` の定義が2つあった

`build_submission_package.py` だけが **MiB（÷1024²）**、他は **MB（÷10⁶）** を使っていた。
同じ 2,990,589 バイトの動画が **2.85 と 2.99 の両方**で文書に載っていた。
**要項の上限「200MB」は10進**なので、10進に統一した。

## 2. 意思決定

| ID | 決めたこと | 理由 |
|---|---|---|
| **DEC-37** | **拡大は `lanczos` を明示する** | 既定の bicubic だと焼き込み文字が二重ににじむ。素材が 720×720 なのを 1280 幅へ拡大するため必ず通る経路 |
| **DEC-38** | **焼き込み文字は半透明の下地（`box=1`）の上に置く** | 白文字だけだと明るい卓上で消える。**背景が変わっても読めることを保証できるのは下地だけ** |
| **DEC-39** | **`ffmpeg` の stderr が空でなければ失敗として扱う** | drawtext は**文字を落としても終了コード 0 を返す**。`-v error` 指定下で出力があること自体が異常 |
| **DEC-40** | **動画に焼く数値は、図と同じ実測 JSON から読む**（素材 run からは読まない） | 素材 run は5エピソード、図は20エピソード。**出典が2つあると同じ動画の中で数字が割れる** |
| **DEC-41** | **`MB` は10進（÷10⁶）に統一する** | 要項の上限が10進。MiB と混ぜると**同一ファイルが2つの数字を持つ** |
| **DEC-42** | **「人の目視」項目には、判定を書かずに材料だけを機械が揃える** | 機械が判定してはいけない＝**材料を揃えてもいけない、ではない**。材料が無いから誰も見なかった |

### 7-2. 欠陥2 の原因は「幅」だった（罫線と単語分断は同一原因）

最小の HTML を2通り作って実測した。

| 指定の仕方 | 罫線 | 幅 | `Milk→Can→Bread` |
|---|:-:|:-:|---|
| CSS（`border-collapse` / `border` / `width:100%`） | **出ない** | **効かない** | **`Brea` と `d` に分断** |
| **HTML 属性（`border` / `cellspacing` / `cellpadding` / `width`）** | **出る** | **効く** | **1行に収まる** |

> **LibreOffice の Writer/Web は、表でも CSS を見ずに HTML 属性を見る。**
> **画像の幅とまったく同じ型である**（落とし穴 #15）。∴ **この経路では「見た目は属性で与える」を原則にする。**
> **単語が途中で切れていたのは文字組みの問題ではなく、幅指定が無視されて列が狭かったせい**であり、
> **1つの原因が2つの症状に見えていた。**

## 8. 追補 — 目視6項目の材料を「成果物から測る」形にした（J-0 の準備）

### 8-1. 旧版の材料は「意図の証拠」でしかなかった

項目2（倍速の倍率が画面に出ているか）の材料は、旧版では
**「生成コードに倍速の焼き込みがある」**だった。**これはコードを読めば分かることであり、
出来上がった映像の証拠ではない。** ——`%` の件で、**コードにあるのに映像から消えていた**ことを既に経験している。

**∴ 成果物そのものから測るように変えた**（DEC-46 / C-30）。
映像を1秒刻みで走査し、右上の**黄色バッジの画素数**を数える。

| 測ったこと | 結果 |
|---|---|
| バッジを検出した区間 | **80〜103 秒**（連続1区間のみ） |
| 検出しなかった区間 | 残り **158 秒すべて** |
| 対応関係 | バッジは `speed != 1.0` のときだけ描かれる ∴ **検出区間＝倍速区間** |

**これは「2倍速は1区間だけで、そこには必ず表示がある」という主張の直接の証拠**になる。
